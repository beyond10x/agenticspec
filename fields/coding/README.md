# Field: coding

Agents that change software. They read and edit files, run commands, and bring their changes into
repositories through change requests, issues and queues of work.

The field adds no block of its own: every concept it needs is shared with other kinds of work and
lives in a pack (`field.yaml` lists them):

| pack | blocks | what the field takes from it |
|---|---|---|
| `packs/source-control` | `scm.forge`, `scm.repository`, `scm.check`, `scm.change` | where code lives and how a change gets in: revisions, references, check runs, change requests whose approval binds one head |
| `packs/tracking` | `tracking.issue`, `tracking.board`, `tracking.queue` | what is to be done: issues linked to change requests, boards, work queues with claims |
| `packs/files` | `files.toolset` | the file tools: `read_file`, `write_file`, `edit_file`, `list_dir`, `search`, `move`, `copy`, `delete` |
| `packs/shell` | `shell.toolset` | `run_command` |

A concrete forge, issue tracker or agent harness is a binding of these blocks, never a block.

## Architectures

- `architectures/auto-merger.yaml`: an agent woken by a recorded check result merges a change
  request whose checks passed at the head a reviewer approved, under a grant its owner issued.
  `agenticspec sim check` accepts it; `task check:fields` checks it.

## Data of the field

- `profiles/coding.yaml`: the behaviour profile of coding agents and their owner, the simulator's
  input. Every experiment under `experiments/` names `field: coding` and runs it.
- `kpis.yaml`: the field's KPIs (merges, reverts, merge conflicts, a change shipped wrong, docs
  changed with code, a check run on an unrelated revision). Each names the core block whose events
  it reads; the core catalogue holds none of them. The packs keep their own KPIs.
- `rows.yaml`: rows the field registers in catalogs of the core: the permission mode
  `accept-edits`.
- `words.txt`: the words only this field uses. `task check:neutral` refuses each of them in the
  core blocks and the core KPI catalogue.
