# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- Requirements: a top-level `requirements:` key of an architecture, entries `{kpi, at_least | at_most | equals, part?, window?}`, outside the nesting digest and the revision digest. `agenticspec sim check` refuses a KPI id no stage knows (`requirement_kpi_unknown`) and an entry of the wrong form (`requirement_invalid`), and prints each requirement under `requirements` with its stage (`check`, `evaluation`, `operation`, `cloud`), its state (`met`, `missed`, `undecided`) and its value: a KPI of the architecture as a whole or a gate count is decided at check; a missed one is reported and does not refuse the document. A cloud KPI is written `cloudspec:<id>`. `agenticspec sim run` decides each requirement on what the simulator measures; the search ranks a feasible variant by requirements missed before its fitness, `fit` stops after the round in which a variant first meets them all, and the result carries each requirement's state (`requirements`, `baseline.requirements`, `best.requirements`, `variants[].requirements_missed`). A result without requirements is the same bytes as before
- `agenticspec deploy bundle` carries every document a nested architecture references, the nesting chain resolved, in `nested`: keyed by its canonical digest (the pin), with the parts that refer to it, its exact bytes in `content_base64` with their `sha256`, and the parsed `document`; the units, packing and contract read the architecture flattened. `agenticspec deploy check` resolves the architecture from those documents and refuses a pin the bundle carries no document of (`nested_document_missing`) and a carried document whose bytes or digest do not hold (`nested_document_mismatch`). The bundle's `requirements` are checked like `sim check` does (a refusal is a finding of `not_admitted`) and each carries its stage, state and value. New fixture: `bundles/team-with-console.local.yaml`
- A part's settings are typed per block, from one table (`blocks/settings.yaml`): each setting a part of a block may carry, with its type (number or integer with unit and range, boolean, enum, duration, string, the name of another part, shares), its default and the contract ports it narrows; an enum is the block's own where the block declares one (a pool's `kind`, a sandbox's `isolation`). `agenticspec sim check` refuses a setting the part's block does not declare (`setting_unknown`) and a value outside its type or range (`setting_invalid`, for example `capacity: many` on a pool), each naming the part, the setting and what was expected; both are gate KPIs, so every variant in `result.json` counts them. The contract copies the settings the table marks, and each block page of the docs site lists its settings with type, unit, default and the ports they narrow
- A UI of your own in a deployment bundle: any key under a binding's `ui:` other than `operator` and `control-plane` is a UI you built, `ui.<name>: {source: {archive: <file>, digest: sha256:<hex>}, export: <ingress>.<protocol>, upstream?, port?, bind?}`. `agenticspec deploy bundle` adds the unit `<name>` (`kind: service`, `roles: [ui]`, static code) and carries your archive byte for byte in `files`, beside the operator and control-plane UIs. It refuses an archive that is not its digest (`ui_archive_mismatch`) and an export no ingress has (`ui_export_unknown`). `source: {ess_ui: <file>}` is refused with `ui_build_needs_toolchain`, because the pages `ui generate` writes need node and vite to build; name the archive you built instead. The accepted list holds the role `ui`
- The control-plane UI: `agenticspec ui derive --control-plane` and `ui build --control-plane [--prediction <result.json>]` add pages across parts beside the operator UI. The pages are Inbox, Activity, Operations, Metrics (each KPI with the simulator's prediction of the same revision), Architecture (read-only) and Events (the level's channel as a live log), plus tiles on the overview. They are selected by port class and by the configuration/administration split, never by view name. A configuration command, a command only report-issuing actors may issue, and machine traffic are never offered. `ui serve` serves the control-plane UI at `/control/`, and `ui conform --architecture` checks its reads. A binding's `ui: {control-plane: {port, bind, upstream}}` adds the bundle unit `control-plane-ui` (`roles: [control-plane-ui]`, static code), which can run beside `operator-ui`. Golden examples for `workstation` and `team-with-console` are under `ui/views/examples/`, held by `task check:ui`
- `agenticspec ui serve` and `agenticspec ui conform --architecture` work from a released binary alone, in any directory: the fixtures they answer from (every view fixture, channel script and scripted outcome, about 114 KB) are built into the binary, and the contract is derived with the port and KPI catalogues built into it. `ui serve --fixtures <dir>` answers from a directory of your own (`<view>.json` files, `scripts/`, `outcomes.json`); `fixtures_unreadable` now refuses only such a directory
- `agenticspec ui serve <architecture> [--contract <file>] [--port <n>]` shows the operator UI of an architecture with no runtime: it derives the default control plane and serves it on 127.0.0.1 (port 7430 by default), the operator app at `/` and the runtime interface below `/ingress/operator` answered from fixtures: R1 from the block fixtures, R2 from the channel scripts with resume from a cursor, R4 recorded (`/fixture/commands`) with the outcomes of `ui/views/source/outcomes.json`, R5 allowing every action
- `agenticspec ui conform --architecture <file> [--contract <file>] [--source <url>]` checks a running server, such as a runtime's own adapter, against the default control plane of an architecture with no plan: each part's views answer rows of their declared shape, the level's channel resumes from a cursor without repeating an event, R4 carries out what R5 allows and refuses what it withholds, R5 answers at every scope, and a request without credentials gets 401. It exits non-zero and names each failed check; `docs/deployment.md` shows how a runtime proves it answers the interface

- The building blocks declare their cross-block causation as ESS bindings (`blocks/components.yaml`): an admitted gateway call starts its inference, and the authority's decision, approval or rejection decides a harness tool call. `task check:layers` counts bindings among the dependencies, and `task check:blocks` requires a scenario per binding. Causations ESS cannot express yet have reproductions under `design/ess-repro/`
- `agenticspec sim ports` derives the ports of the building blocks, where the specification waits on the world, into `blocks/ports.json`: each port's kind (outbound, clock, principal), intent, reports and protocol. `--check` compares the file's digest with the blocks without calling `ess` (`task check:ports`), `--expect` lists every difference from an expected list
- `agenticspec sim contract <architecture>` derives and checks the contract of an architecture (`agenticspec-contract/1`): the ports its parts use with their protocols, narrowing settings (an agent's `role`, an `on_event` trigger's `event_name` and `source`) and instances, a routing invariant per link (a runtime's `run` and `model_call` links among them) in a small predicate language, and the border; `--check` checks a written contract. `docs/contract.md` describes ports, the contract and the predicate language
- Every architecture page and catalog entry of the docs site has a "Contract" section and its contract file to download (`<name>.contract.yaml`)
- KPIs of an architecture as a whole, read from its document before any simulation: `agents_total`, `principals_total`, `human_touchpoints`, `autonomy_depth`, `model_call_paths`, `ungated_model_calls`, `single_points`, `border_parts`, `egress_targets`, `shared_workspaces` and `capacity_ratio`. `agenticspec sim check` reports them (and names the single points), `result.json` carries them for every variant, the KPI catalogue lists them under the block `architecture`, each architecture page and catalog entry has a section "The architecture as a whole", and the catalog index compares every architecture on them in a sortable table
- agenticstudio is live: every query, apply, check and simulate on a draft is a tool call of a studio session (`/api/sessions`), each new revision and each answered call reaches every page open on the draft at once over its event channel (`/api/drafts/<id>/events`), and a draft's revisions can be listed and read (`/api/drafts/<id>/revisions`). When the architecture file a draft was opened from changes on disk, the change becomes the draft's next revision on every open page. `simulate` answers the mean of each KPI over a few seeds with what the KPI catalogue says it measures
- `agenticstudio-mcp`, the agent channel: an MCP server over stdio whose tools `query`, `apply`, `check` and `simulate` drive a draft of a running `agenticstudio serve`; a refusal names the rule and the error, a simulate explains each KPI, and every page open on the draft shows each change live (`docs/studio.md`)
- `agenticspec sim check --json <architecture>` prints one `agenticspec-check/1` JSON document on standard output, also when the architecture is refused: `valid`, every violation with its `rule`, `gate`, `subject` (the part, or the link as `<from>-><to>:<carries>`), `part`, `link` and `message`, sorted, and the count of every rule. The exit code and the output without `--json` are unchanged
- `agenticspec sim` simulates more of an architecture: an agent that reaches several model parts splits its calls by its `model_share` and each call is priced by its model's route; a runtime part given runs (a `run` or `order` link, or a trigger) executes their steps, model calls and person steps; an `on_event` trigger fires when the simulation emits its event (`agentic.work.TaskCompleted` and seven more), optionally only for the part its `source` names, and a trigger may wake a runtime
- `agenticspec ui generate --path <doc> --out <dir>` turns an `ess-ui/1` document into a Vue app (pages, router, typed client) over the design system `ui/kit`, refusing any construct it cannot draw by its node path. agenticstudio's page is now that app (`ui/studio`, from `studio/studio.ui.yaml`): the graph fills the page inline with pan, zoom and part selection, a side panel holds the patch, the draft and the parts, one theme switch covers it all, and every control looks like the docs site. `agenticstudio serve` takes `--www` and answers `/api/views` and `/api/commands`; `task studio:build` builds the app, `task check:ui-kit` and `task check:studio` gate both
- agenticstudio, first slice: `agenticstudio serve --root <dir> --port <n>` opens an architecture of `architectures/` as a draft in the browser, applies a patch (`agenticspec-patch/1`: `set` and `add` over the facts `part`, `setting`, `link` and `marker`) as one revision or refuses it whole with the rule's position and error, and shows the graph, the parts and the check. Drafts are held in memory. `task check:studio` runs its browser test (`docs/studio.md`)
- The architecture block records where an entity of a lower block sits: `agentic.architecture.Placement` (architecture, revision, part path, copy, entity name and id), recorded by the runtime through `PlaceEntity` and read through the view `Placements`, filtered by part path, copy and entity name. A row of any block view is in scope of a part when its own id, or an id field of its view one hop away, is placed to that part
- `agenticspec ui panels` writes the block panels from the building blocks: `ui/views/blocks.ui.yaml`, an `ess-ui/1` document with one panel per view of `blocks/` (its fields as columns, its first field as row key, an enum such as `state` as a badge, live updates from the events of the view's entity, a scope of architecture, part and instance) and a gallery page per block, the fixtures the panels render against in `ui/views/fixtures/`, and the digest of its inputs in `ui/views/blocks.sources.sha256`. `--check` compares a fresh generation byte for byte; `task check:ui` runs it and holds `ess ui check --model blocks` at 0 errors and 0 warnings
- `blocks/components.yaml`: one component owning every block, served over HTTP, and a `Viewer` actor for the agent, architecture, delegation, experiment, KPI, principal and process blocks, so every view of `blocks/` is readable from an `ess-ui/1` document
- Nested architectures: a part `{ block: architecture, ref: <file>, digest: sha256:<hex> }` is another architecture document, and a link reaches one of its border parts as `<part>.<border part>`. `agenticspec sim check` resolves the references recursively and refuses a missing file, a digest mismatch (expected and actual), a cycle, an address off the nested border and a nested document its own check refuses; its output lists the nested architectures with their digests. `agenticspec sim digest <file>` prints the pin: the SHA-256 of the canonical JSON of the document's parts, links and border. The simulator flattens a nested architecture into parts named `<part>.<inner part>`, renaming the parts an inner `model_share` or trigger `source` names; an inner part keeps its `role`; the graph draws it as one box with its border parts as ports. Example: `architectures/team-with-console.yaml`, which nests `architectures/console.yaml`; its steward has `role: orchestrator`, and `profiles/coding.yaml` gives that role an `answer_seconds` so the steward answers the agents it orders
- `agenticspec ui generate` draws the block panels: one Vue component per widget of the document (`widgets/<Widget>.vue`, the same file for the same widget in every document) with its parameters as props, a page section that uses a widget with its arguments, a navigation region as the docs site's sidebar (a Pages button on a narrow screen), `live` with `effect: refetch` coalesced over `coalesce` and `effect: insert_or_patch` by `match` (with `only_if: matches(params)`), `as: json`, and a widget's scope (`source`, else `/scopes/<architecture>/<part>/<instance>` under the app's own base); every other construct is refused by its node path. A document that names no theme follows the system theme. `ui/views/gallery` is the gallery of the block panels over their fixtures, with no server: `task views:build` builds it, `task check:views` runs its unit tests and its browser test (every panel shows its fixture rows; axe-core and overflow at 1366x768 and 390x844 in both themes). The kit shows a UUID short, a JSON value by its entries and a named state by its name, and a table that scrolls sideways can be reached by the keyboard
- The runtime interface of the generated UI, `ui/runtime.openapi.yaml`: reads, a channel resumable from a cursor, the placement views, commands and the action set, at `{root}/scopes/{architecture_id}[/{part path}[/{instance}]]`, each request authenticated. `agenticspec ui conform [--source <url>] [--plan <file>]` checks an adapter against it (scoped reads, resume from a cursor, refusals, the action set against the grants, a request without credentials), against the fixture source of `ui/views/source/` when no source is given; the gallery answers a scoped widget the same way
- An action that sends a command shows only while the action set of its scope (`GET {source}/api/actions`) allows the command, and an action takes `visible`, which may read `actor.may(<command>)`; a source without an action set shows every action. The generated client sends the cookies of the host's sign-in, also to a source on another origin
- `agenticspec sim contract <architecture> --suite <suite.json> --out <cut.json>` cuts the conformance suite of the building blocks to the scenarios about a command of a port of the contract, and `task contract:conform -- <architecture.yaml>` runs the cut of the cached suite on the ESS interpreter, printing the count kept against the whole suite (`architectures/workstation.yaml`: 195 of 702)
- `agenticspec sim trace <architecture> --profile <profile>` writes the port uses of one simulated run as a trace (`agenticspec-trace/1`): model calls inside their gateway calls, build claims, questions and their forwards, channel deliveries, posts and trigger firings, with begin, end, nesting and counterparty. `agenticspec sim contract <architecture> --trace <trace>` checks every routing invariant of the contract on it: `held`, `violated` (naming the link and the event, exit 1) or `not_checked` when the trace does not record a port the invariant names
- An architecture document may declare its ingresses (`ingress:`): per audience (a principal part) an interface that selects commands (`principal`, `plays` of an actor's administration commands), views, feeds and KPIs, and its exports (`http`, `event_stream`, `cli`, `tool`, `agent`, `metrics_scrape`, `ui`). `agenticspec sim check` refuses an ingress by 14 named rules, reading `blocks/ports.json` (`--ports`) and `kpis/catalogue.yaml` (`--kpis`), and `agenticspec sim contract` writes each interface resolved into operations in the contract's `ingress` section. `architectures/workstation-ingress.yaml` is the worked example
- `blocks/ports.json` lists each actor's commands and per domain its commands with their role (internal, report, intent, configuration, administration), its views and its events
- The architecture block declares `Ingress` and `Export` with `AddIngress`, `AddExport` and the `Ingresses` view, and a contract records its ingresses
- Run and runtime lifecycle in the building blocks: a new block, `deployment` (layer 9), installs an architecture revision on a runtime, drains it (no new runs, started runs end) and rolls it back to the installation it replaced; an architecture run is queued, running, waiting, done, failed or cancelled and keeps the revision and binding it was queued under. A run, a firing and a harness session take their identity from the caller, so a repeat is refused and starts nothing. A trigger declares what a firing does for a subject that already has a started firing (another, skip, queue, replace). A tool result or an answer that could not be read is recorded as such (`CouldNotRead`), and a restarted session records the session it replaces and the lineage it belongs to (`RecordRestart`). Eight KPIs for them in the catalogue
- The core blocks name no field's vocabulary. The coding field (`fields/coding/`) now holds its behaviour profile (`profiles/coding.yaml`, moved from `profiles/`), its 8 KPIs (`kpis.yaml`, moved out of `kpis/catalogue.yaml`: `proposals_merged_share`, `revert_rate`, `open_to_merge_seconds`, `merge_conflicts`, `task_to_merge_seconds`, `false_completions_shipped`, `docs_changed_with_code_share`, `vacuous_check_share`), the rows it registers in core catalogs (`rows.yaml`) and the words only it uses (`words.txt`). `task check:neutral` refuses those words in `blocks/` and `kpis/catalogue.yaml`; every experiment names its `field:`, and the catalog page groups its entries by field
- A `store` block (layer 3): stores of five kinds (record, artifact, key-value, semantic, graph) with a scope and a retention, records put, revised by compare-and-set, expired and deleted, artifacts addressed by their digest and never revised, and every get and query recorded with digests and a count. Four store KPIs and `evidence_unresolved` join the KPI catalogue
- `agenticspec blocks lift <session>` lifts a session into rows of the building blocks: tasks, the runs and assignments that worked them, their steps, questions and messages, each naming the node it came from, with the fields the session does not record listed in `not_recorded`; `agentic.resource.Claim` is reported as not observable. The rules are `queries/blocks.sq`, so `agenticspec query queries/blocks.sq --transcript <session>` shows them too
- `agenticspec blocks scenario <session> --architecture <a> --profile <p> --map main=<part>` writes a draft scenario: each outside input of the session (a prompt by a human, a delegate or another session; not a harness prompt) at the main agent's part, and the block events of the rows its turn caused as `then`; inputs no turn received are listed as `unjoined`
- A scenario's `given` holds `rows` of any block entity, each checked against the blocks: entity, field names and types, lifecycle state, and every required field given or named in `not_recorded`
- `agentic.channel.Message` names the turn of the receiving session that read it (`received_in_turn`, set by `MarkRead`)
- `agenticspec sim run --events` also writes `events.jsonl`, the run the result's timeline samples as an event log: one line per moment that is a block event (`agentic.work.TaskCreated`, `agentic.resource.ClaimQueued`, ...), with its sequence number, time, architecture, part path, copy and subject key (`task-3`, `claim-5`), the same bytes for the same seed. `result.json` stays byte for byte the same with or without it
- The binding of an architecture (`agenticspec-binding/1`), with a `refines:` chain and a `packing:` section: which parts share a unit (`core`, `agent`, `service`, `job`, `scheduled`, `store`, `model`, or `external`) under a strategy (`single` by default, `by_kind`, `by_part`, `groups`) or as listed units. `agenticspec packing default <architecture> [--strategy <strategy>]` prints the resolved section to paste and change. `docs/deployment.md` describes the binding, packing, admission and the bundle
- `agenticspec deploy bundle <architecture> --binding <file>` admits an architecture with its contract, binding and packing and writes its deployment bundle (`agenticspec-deployment/1`): one YAML file with the architecture, contract, binding, packing, agent documents and pinned runtimes inline, each by digest, and per unit its code (an agent unit stays an agent by its agent document and the role `agent-runtime`), claims with volumes, isolation, checks, schedule, secrets, egress, roles and contract ports. The same inputs give the same bytes; a refusal writes nothing and names every finding (`part_unpacked`, `part_packed_twice`, `per_split`, `shared_state_split`, `link_without_transport`, `isolation_unmet`, `scheduled_with_inputs`, `core_count`, `unit_not_hosted`, `agent_document_missing`, `agent_document_digest`)
- Secrets and egress are declared per part in the binding, by name (`parts.<part>.secrets`, `parts.<part>.egress`: a part, or a destination the target resolves, optionally with the secret its link authenticates with), and each unit of the bundle carries them, every egress entry with the part it starts at. Admission refuses a link that leaves its unit to a destination its part does not declare (`egress_undeclared`), a secret no part of the unit declares (`secret_undeclared`) and anything that looks like a secret's value where a name belongs (`secret_value`), naming where, never the text. `agenticspec deploy check <bundle>` admits a written bundle again from what it carries and refuses a digest that does not hold, an undeclared reference or a value
- Fixture bundles under `bundles/`, one per catalog architecture and test binding, with `bundles/sources.sha256` (`task bundles:generate`; `task check:bundles` in the gate; `task slow:bundles`) and the copy of the translator's accepted unit kinds and roles
- The `deployment` block records a deployment of a revision onto one scope of a target, from its request to its run: requested, bundled, translated, realizing, running, degraded, stopped or failed, refused before anything is recorded (`NotReleased`, `NotAdmitted`, `ScopeTaken`) or after its hand-over (`CoverageRefused`, `TargetRefused`), with its units, their target objects and ready replicas (views `Deployments` and `Units`)
- Every architecture has a default control plane: the ingresses `operator` (audience `control.operator`: every principal port answered, the administration commands, views and events of all parts, over `http`, `event_stream`, `ui` and `tool`) and `metrics` (audience `control.monitor`: the KPIs a runtime computes, over `metrics_scrape`), unless it declares an ingress of that name or sets it to `none`. The rule values `principal: all`, `plays: administration` and `metrics: computed` select them; `agenticspec sim check` refuses a part named `control` and a misused reserved name by 3 more rules. `agenticspec ingress default <architecture>` prints the section to paste into the document and change
- `agenticspec ingress project <architecture> --out <dir>` writes, per ingress with an `http` export, its `ess-http/1` protocol binding and its OpenAPI document; `--check <dir>` compares written projections with a fresh one (`task check:projections` holds those of `workstation-ingress`)
- The component of the building blocks is reached by network and accepts the entry commands an ingress may export, so ESS accepts an `ess-http/1` binding of them; among them `Answer`, `ApproveDecision`, `RejectDecision` and `SendMessage`, which a derived UI sends as actions
- `agenticspec ui derive --path <architecture> [--contract <file> --ports <file>] --out <name>.ui.yaml` writes the operator UI of an architecture as one `ess-ui/1` document over the block panels: an overview per level (the parts table, the reach table filtered by part, the graph, the policies and marked places), a page per part with its instance panel first and a frame per domain it uses, a page and a navigation section per nested architecture (with an `instance` choice when it runs more than one copy), a live channel per level, the actions of the contract's principal ports as row actions and of a border link as header actions (each `visible` by `actor.may(<command>)`), its fixtures and a layout file. Without a contract the domains come from the architecture alone. `--check` compares. An architecture's top-level `view:` key labels, orders, hides and groups what the UI shows and nothing else; the simulator, the check and a catalog result's digest ignore it (`docs/architectures/`). `ui/views/examples/` holds the UI of `workstation` (from its contract and `blocks/ports.json`) and of the 37-part fixture; `task ui:derive` writes them, `task check:ui` holds them at 0 errors and 0 warnings, and `task check:examples` runs their browser test at 1366x768. `agenticspec ui generate` draws layout areas with shared frames, header actions, a filter over two fields and row actions that send a field of their row
- `ui/views` is a Vue package (`@agenticspec/views`): the block panels, a part page and an overview drawn from a derived UI's layout, every panel of a block, each parameterised by `source`, `architecture`, `part` and `instance`, and the runtime of the panels (`installViews`, `mountViews` for an island). The same components are a bundle of custom elements (`<agentic-part-panel>`, `<agentic-overview>`, `<agentic-panel>`, `<agentic-block-panels>` and one element per panel, `task elements:build`) that draw in the light DOM with the host's `--kit-*` tokens and send `agentic-navigate` and `agentic-command` DOM events instead of acting. A server on another origin answers CORS with credentials, since the client sends cookies. `task check:elements` runs its unit tests and a browser test in a plain page and a React page; `ui/views/examples/host-slot.ui.yaml` places the element through a host slot that `ess ui check` holds. agenticstudio's draft view shows the panels of a part's block from the package on the panels' fixtures
- Scenarios can make a part, or one dependency of a part, unavailable: `unavailable` entries name the part (and its `dependency`) with `from` and `for`, and `then.parts` says what each remaining part shows: a view by its block name that answers, is empty or shows an error by its block name, a command that is accepted or refused, the status its process exits with before it listens, and whether the rest of it answers. `agenticspec sim scenario check` refuses an unknown part, dependency, view, command or error by name; `run` makes a pool or gateway lose its capacity, a principal go away or a border part refuse its inputs (rule `part_unavailable`), reports what it cannot model, and writes every observable as `not_checked` with the reason for a runtime to check. Four examples for the workstation in `scenarios/workstation/`; format and the contract for a runtime in `docs/scenarios.md`
- A deployment bundle says what its target serves: each export of each ingress is an entry of `ingress` with the `unit` and `part` that serve it, its `bind` (`loopback` or `all`) and, when the binding gives them under `ingress.<name>.exports.<protocol>`, its `port` and `address`; a unit's checks carry the `port` the binding gives under `checks.<unit>`; a volume carries its `mount`, the absolute path from `parts.<part>.volumes`
- A binding may take runtime images from the target's local store (`target: {images: local}`), each pinned by `tag`, `digest` (its config id) or both, and the bundle's `runtimes` carry them as given; refused as `image_unpinned` when a runtime names neither
- Any part may be external, with the `reach` the target finds it by (`{name}` or `{address}`, beside `units:` as `{part, reach}`, beside a strategy as `packing.parts.<part>.reach`); the bundle's packing lists each external part as `{part, kind, reach}`
- Every egress entry of a unit carries `name`, what its target resolves (an external part's reach, the unit a link crosses to, a named destination), and `address` when the binding gives one; a named destination may name its `address` (a CIDR block, `<host>:<port>` or `{namespace, labels}`), and one without it is marked `unresolved: true`
- `target.network_policy` (`enforced` or `not_enforced`) and `parts.<part>.network: isolated` in a binding: a part isolated on a target that enforces no network policy is refused as `network_isolation_unmet`. `deploy bundle` and `deploy check` refuse a volume without an absolute mount as `volume_mount_missing`
- `agenticspec ui build <architecture> --contract <file> --out <dir> [--api-base <path>] [--archive]` writes the operator UI of an architecture as static files from the binary alone, with no node and no app of your own: the operator app built into the binary (`index.html`, `app.js`, `app.css`, 207 KB) and its data files, `views.json` (the layout `ui derive` derives), `contract.json`, `ports.json` and `config.json` (the adapter's base path, `/api/` by default). The app reads them at start and calls the runtime interface at `<api_base>/scopes/<architecture>/<part>`; a part page shows the actions the action set allows and sends them as commands. The same inputs give the same bytes; `--archive` writes `<dir>.tar` with sorted entries, mode 0644, owner 0 and time 0, and prints its `archive_sha256` (`docs/deployment.md`). The app's sources are `ui/operator/`; its build is committed in `ui/operator/built/` with the digest of its sources, which `task check:operator` compares, and `task operator:build` rebuilds
- A binding with `ui: {operator: {port, bind, upstream: {unit, port}}}` makes `agenticspec deploy bundle` add the operator UI as a unit of its own: `operator-ui`, `kind: service`, `roles: [operator-ui]`, `code: {kind: static, archive: operator-ui.tar, digest}` with the archive `ui build --archive` writes for the same architecture and contract, built in-process and carried base64 in the new optional member `files`; `upstream: {unit, port, path}` names the unit whose adapter the page reads (the core by default, `path` `/api/`), and the ingress entry of the operator's `ui` export names the UI unit. `deploy bundle` refuses an upstream that names no unit (`ui_upstream_unknown`) and a UI that does not build (`ui_build_refused`); `deploy check` also refuses a carried archive that is not the unit's digest (`ui_archive_mismatch`). The accepted list holds the role `operator-ui`; `bundles/workstation.operator-ui.yaml` is the new fixture. A binding without `ui:` gives the same bundle as before
- `agenticspec ui panels` also writes `ui/views/blocks.model.json`, the part of the compiled blocks a derivation reads, so `ui build` derives with neither `ess` nor `blocks/`; the part page of `@agenticspec/views` takes `allowed`, the commands the action set of its scope allows
- `agenticspec_render::page::render(&Page)` draws any graph in the visual language of the architecture pages as one self-contained HTML page: a neutral render model (`agenticspec-render-model/1`: nodes in groups, ports, edges, regions, marks that are refusals or information, panels) with its JSON Schema in `crates/agenticspec-render/schema/render-model.schema.json`. The architecture pages go through the same renderer (`agenticspec_render::architecture::page` and `::graph`); their stylesheet gains the rules for regions, refused ports, refusal rings and counted edges. A region is a frame drawn around the cards of its nodes, nested regions included, and an edge to a node in a region lands on that node's card; a port names what it runs over (`via`), and an `unresolved` port leaves its row as a dashed stub named by its refusal marks. Architecture pages draw a `per` part beside its owner inside one frame
- A binding may pin the agent units' runtime as `runtimes.agent-runtime: {image, tag, digest}`, under the same `target.images` rules as the core runtime (from a registry by its digest; from the local store by tag, config id or both, else `image_unpinned`): the bundle's `runtimes` carry it and each agent unit's `code.runtime` names it. Without it the target binds the role `agent-runtime` as before
- A bundle's `agents.<digest>` carry `content_base64`, the exact bytes of the agent document file, beside the parsed `document`; `<digest>` is the SHA-256 of those bytes. `agenticspec deploy check` decodes and hashes them and refuses an entry whose bytes are missing, are not its digest or do not parse to its `document` (`agent_document_mismatch`)
- An agent unit of a bundle carries `shape`: `service`, `job` or `scheduled`. A scheduled one carries `schedule`, the cron rule a binding gives with `packing.parts.<part>.schedule: <cron>` (five fields; such a part runs as a scheduled unit, the cron counting as its clock); `packing.parts.<part>.shape: job` is another spelling of `schedule: job`. The resolved packing lists a scheduled unit's `schedule`
- A scheduled unit whose binding gives no cron rule carries the one that states its schedule's `every` exactly: N minutes dividing 60 (`*/N * * * *`), N hours dividing 24 (`0 */N * * *`), one day (`0 0 * * *`) or one week (`0 0 * * 0`). `deploy bundle` and `deploy check` refuse any other interval (`90m`, `7h`, `45s`) as `schedule_not_cron`, naming the unit, the part and the interval; `deploy check` also refuses a unit that carries another rule. A rule the binding gives still wins
- The operator UI's unit takes its claims and check ports from the binding like any other unit: `claims.operator-ui` and `checks.operator-ui.<ready|alive>.port` (before, always 500 millicores and 512 MiB, and the export's port)
- The render model has a top-level `groups: [{name, colour?, icon?}]`: the cards, frames and legend swatch of a group take its `colour` (a hex colour, `rgb()`, `hsl()` or a named colour of a fixed list; anything else is refused) and its cards its `icon` (one of the crate's icon names, or a text of 1 or 2 characters). A group not listed keeps the palette
- A badge of the render model with `on: panel` is not drawn on its card but listed in the table "Details" under the graph (`on: card` is the default)
- An edge of the render model with a `count` is drawn heavier: 2 or 3 wider than one, 4 or more wider again, its arrowhead the same size
- Each core or service unit of a bundle may run an image of its own: a binding names it as `parts.<part>.image` or, on a unit listed under `packing.units`, as its `image`, each `{image, tag, digest}` under the same `target.images` rules as `runtimes.core` (`image_unpinned` from the local store with neither tag nor digest). The unit's image wins over its parts'; parts of one unit that name different images are refused as `unit_image_conflict`. The unit's `code.runtime` names its image and the bundle's `runtimes` carry every image a unit runs. `deploy check` applies the same rules

### Changed

- A scenario's `then` names block events by their full name, as the blocks declare them (`{ event: agentic.work.RunStarted }`, not `run_started`), and a refusal by the block command refused, its error and the rule of the run (`{ refusal: agentic.resource.RequestClaim, error: agentic.resource.NoTimeLimit }`, `{ refusal: agentic.channel.SendMessage, rule: control_without_proof }`), in place of `event: refusal`. `sim scenario check` refuses an event no block declares as `unknown_event`, naming the nearest declared event (so an old name like `run_started` points to `agentic.work.RunStarted`), and a command or error no block declares for it as `unknown_refusal`. Its other problems carry codes of their own: `architecture_digest_mismatch` (`run` refuses before the simulation starts), `profile_digest_mismatch`, `architecture_refused`, `input_not_at_border`, `invalid_row` and `fixture_without_part`; a scenario whose problems all have one code exits with it, one with problems of several codes with `scenario_refused`. The trace of `scenario-result.json` drops `name` and carries each refusal's `command`. The scenarios under `scenarios/workstation/` and the drafts of `agenticspec blocks scenario` use the new form
- `agenticspec sim` runs a process part like a runtime when it is given runs (a `run` or `order` link, or a trigger): each run executes the steps of its program, `steps` (1 by default), each a turn of the profile role the part names by `role`, and the part reports its runs in its per-part KPIs (`tasks_started`, `run_steps`). `sim check` accepts a trigger link that ends at a process part; `trigger_target_not_agent` refuses one that ends at a part that is not an agent, a runtime or a process
- `runtimes.core` is the image of the core unit only. A service unit without an image of its own names the role `core-runtime`, and a core or service unit that holds a runtime part and has no image is refused as `unit_image_missing`, naming the unit and its runtime parts. The split fixture binding names the core image for its gateway and build pool
- `agenticspec sim check` refuses a part block and a link `carries` value that the architecture block (`agentic.architecture.PartKind`, `Carries`) does not declare (`unknown_blocks`, `unknown_carries`, two more gate KPIs in every result). The block now declares every kind the example architectures use: part kinds `authority`, `work`, `experiment`, `kpi`, `question`, `process`, `delegation` and `architecture`; carries `review`, `handoff`, `call`, `context`, `grant`, `proposal`, `spec`, `checkout`, `result`, `report`, `record`, `read` and `run`. A part may also be a block of a pack (`scm.change`), and a link that reaches one carries what the pack names, so a field's architecture passes the check
- The rendered page of an architecture stays readable when the architecture is large: the graph is drawn at its natural size and pans by drag, wheel and arrow keys, with zoom out, zoom in, fit and actual size when it is wider than its card. Beside it, a table of the parts (each selects its part) and a table of the links, filtered by part. Links that carry the same thing into or out of one part share one label and one line through the rows between, a part that several parts of its row send to sits in a row of its own below them, and long lines run straight. The page header wraps on a phone
- `agenticspec serve` resumes `session_events` from `Last-Event-ID` with exactly the events after the cursor: an event published while a reconnect replays is no longer sent twice
- `agentic.harness`: a permission mode is a registered row (`RegisterPermissionMode`, `RetirePermissionMode`, view `PermissionModes`) that a session names by `PermissionModeId`, no longer an enum with `AcceptEdits`; opening a session in an unknown or retired mode is refused. The coding field registers `accept-edits`
- `agentic.workspace`: a proposal's `branch` and `review_ref` are one field, `handback`, the artifact of a store the change is handed back as, on the proposal, on `Propose`, on `ChangeProposed` and in the view `Proposals`
- Experiments name the behaviour profile of their field, `../fields/coding/profiles/coding.yaml`; the committed catalog results changed only in that path and the new `field: coding`
- A work deliverable of kind Artifact names its artifact (`artifact_id`), and its evidence is a list of store records instead of digests
- The contract of every architecture lists the default ingresses it has, so every contract file and "Contract" section of the docs site gains them, and `agenticspec sim contract` always reads the KPI catalogue
- `agenticspec sim check`, `sim contract`, `packing default` and `deploy bundle` accept the same documents: each runs the check, which refuses a part whose block is no part kind of the architecture block, and every part kind derives its ports (`question`, `process`, `delegation` and a nested `architecture` none of their own); a `harness` part uses `harness.session` and `harness.tool-call`
- A deployment bundle names each pinned runtime by its image reference, `<image>@sha256:<digest>`, in `runtimes` and in a unit's `code`; the binding's runtime needs both `image` (without tag or digest) and `digest`. `deploy bundle` refuses an address in the architecture (a key `address`, `host`, `hostname` or `url`) as `address_in_architecture`: an address is the binding's
- A deployment bundle writes the packing's `agent`, `job` and `scheduled` units as `kind: agent` with `shape: service`, `job` or `scheduled` (the packing keeps its own kinds), and a scheduled unit's clock (trigger, schedule, `every`, `next_fire_at`, `policy`, `max_parallel`) moved from `schedule` to `clock`. ### Fixed
